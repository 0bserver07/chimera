# Chimera 0.9.2.3 — run it before you ship it

**Released:** 2026-08-06

A small release with an uncomfortable lesson. 0.9.2.2 was verified after publish
— installed from PyPI into a clean venv outside the repo, `chimera --version`
correct, `import chimera` correct, the fixes confirmed present in the wheel.
Every assertion true.

It exercised nothing a user does first. Within minutes of installing, a user hit
a **five-second wait** for a prompt and a **traceback on quit**. Neither is
reachable by importing a package.

```bash
uvx --from chimera-run==0.9.2.3 chimera --version
```

## Startup: 5.1 s → sub-second

`chimera code` took **5.1 s** to reach its prompt. Profiling on the machine that
hit it:

```
run_code → CodingAgent.__init__ → create_provider
  → registry._ensure_builtins_registered      5.107 s   of a 5.805 s run
     ...essentially all importlib work
```

`_ensure_builtins_registered()` imported **all ten** built-in provider modules —
and the `anthropic` and `openai` vendor SDKs with them — in order to construct
**one**. Talking to Anthropic cost the OpenAI SDK's import.

Provider lookup is now lazy: `get_provider_factory` imports only the module that
owns the requested name.

| resolve a provider | |
|---|---|
| before — eager, all ten | **1942 ms** |
| after — lazy, one module | **566 ms** |
| saving | **1376 ms, 3.4×** |

(The 5.1 s was a cold-cache first run; 1.9 s warm. Either way it was the bulk of
the wait.)

Nothing became unreachable. `_ensure_builtins_registered()` stays for callers
that genuinely enumerate — `list_providers` in the factory's error path,
`chimera which` — and a test resolves **every** registered name from a cold
interpreter with no eager registration at all.

## Quitting no longer looks like a crash

```
Bye!
Traceback (most recent call last):
  ...asyncio/runners.py line 118 → CancelledError
During handling of the above exception, another exception occurred:
  ...chimera/cli/code.py line 873 → KeyboardInterrupt
```

A Ctrl+C landing during asyncio's shutdown makes `asyncio.run` cancel the task
and re-raise — *after* the REPL already printed its goodbye. `run_code` now
catches it. Quitting is not an error.

## The checklist that missed both

Post-publish verification now has to **run** the thing:

```bash
cd /tmp && python3 -m venv v && ./v/bin/pip install 'chimera-run[anthropic]'
time ./v/bin/chimera code < /dev/null                # time-to-prompt
./v/bin/chimera code & sleep 6; kill -INT %1; wait   # quit must not traceback
```

**Both lines.** The first version of this gate had only the redirect — and
`< /dev/null` raises `EOFError`, a different path from `SIGINT`. Measured on the
0.9.2.2 tree: the redirect exits 0 and silent on the exact build that dumps
`KeyboardInterrupt` when you actually press Ctrl+C. A gate that tests only the
easy exit reports green on a crash-on-quit, which is how this shipped.

And verify on a machine that is **not** the dev box. The same release installed
cleanly here and failed on the user's Linux host with
`ERROR: Could not find a version that satisfies the requirement chimera-run
(from versions: none)` — which reads exactly like the package was never
published. It was actually a `pip` shim bound to a dead Python 3.8 while
`python3` was 3.11.7, so pip filtered out every file for `requires-python
>=3.11`. Worth knowing, because the error names the wrong culprit.

## Notes for anyone extending providers

The name→module table (`_BUILTIN_MODULES`) is a claim about another module's
import side effects, so the tests **re-derive** it: each module is imported in a
clean interpreter and its registrations compared against the map. That is not
theoretical — `modal_endpoint`, `xai` and `acmecloud` each *also* register
`compatible` as a side effect, so a map written by reading source would have
been wrong on day one.

The behavioural assertion runs in a **subprocess**, because `sys.modules` in the
test process is already polluted by the suite itself and would have made
"`openai` is not imported" pass regardless of the code.

## Upgrading

No API changes. If you subclass or register providers, note only that
`get_provider_factory` may now import a module as a side effect of lookup —
which is the point.
